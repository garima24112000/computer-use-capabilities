# Evidence

## How to read this evidence

The project has three phases, and each has a section below:

- **Discovery:** an LLM finds the path through the legacy UI once and saves it as a typed,
  versioned artifact.
- **Replay:** the artifact is replayed with no LLM, under normal, exceptional and hostile
  conditions.
- **HITL:** a human takes over the same live browser session when replay can't continue.

Every folder has the command, the exact console output or summary, and the run's own event
log. Nothing here contains secrets or unredacted PII. `uv run python scripts/scan_evidence.py`
checks that, and `tests/test_evidence_clean.py` runs it.

**What was copied vs regenerated**

- **Copied from real runs (never regenerated):**
  - `discovery/`: real Amazon Bedrock runs.
  - `hitl/`: a real recorded session.
  - Local paths in these copies were rewritten to repo-relative ones.
  - The discovery screenshots were taken before the operator id was masked, so it was painted
    over afterwards in these copies, with the same colour the live mask uses.
- **Regenerated by `uv run python scripts/make_evidence.py`:** everything under `replay/`. The
  script starts the target app on free ports and runs each scenario through the real `cua replay`
  CLI.

**Fault injection** uses the target app's test-harness endpoint (`/__faults`). Replay POSTs to
it via `--inject` / `--inject-at`, and every run records it in `harness_faults` and on the
console with a `FAULT INJECTED (harness)` banner. The discovery agent itself is blocked from that
path by `configs/policy.yaml` (`blocked_paths`).

The runs used `uv run cua discover --goal "<goal>" --id <capability> --input ... --output ...`;
the main README has the full form. The full command line was not recorded. Each run's
`manifest.json` holds the exact goal and model, and the artifact holds the contract the
`--input` / `--output` flags produced. The subaccount run used the default
`--approve-mode prompt`, so the operator approved SUBMIT at the terminal (see the `approval_requested` / `approval_result`
events in its `events.jsonl`).

Each artifact was reviewed and approved afterwards with `cua artifact approve`. The `review` block
it adds is excluded from the content hash, so the hash is the same as at discovery.

## Replay scenarios (regenerated)

All `cua replay` scenarios use the 1.1.0 artifacts pinned as `id@version`. Scenario 18 calls
the capability by tool name instead (`cua catalog invoke`), which resolves to the latest
approved version; the tool definitions an agent sees are in
[`catalog/tools.json`](catalog/tools.json) (`cua catalog list --json`). All run against the
target app the script starts (tenant A, or tenant B for drift), with faults reset before each
scenario. Each folder has `command.txt`, `console.txt` (exact output and exit
code), `result.json` and `events.jsonl`. Failure and recovery scenarios also have the masked
`screenshots/` and text `snapshots/`. Exit codes: 0 success, 10 business outcome, 20 failed,
30 escalated.
